# ADR 0005 — REST API design

**Status:** accepted

## Context

The operator console needs to list/inspect assets, drive lifecycle changes, and read
telemetry. The API is the seam between the React frontend and the domain.

## Decision

Resource-oriented REST with intent-revealing status codes:

| Method + path | Purpose | Notable codes |
|---|---|---|
| `GET /assets` | list current fleet state | 200 |
| `POST /assets` | create (starts `provisioned`) | 201 |
| `GET /assets/{id}` | detail | 200 / 404 |
| `POST /assets/{id}/transition` | lifecycle command | 200 / 409 / 422 |
| `GET /assets/{id}/events` | audit log | 200 |
| `GET /assets/{id}/telemetry?metric=&limit=` | recent readings | 200 |
| `POST /assets/{id}/telemetry` | debug/seed ingest (idempotent) | 201 |
| `GET /healthz`, `/readyz` | liveness / readiness probes | 200 |

Key choices:

- **Transition is a command sub-resource**, not a `PATCH /assets/{id}` with a new
  status. It's an *action* with side effects (validation + audit write), and modelling
  it as a command makes intent and failure modes explicit (409 on an illegal move).
- **Correct codes carry meaning:** 201 create, 409 illegal transition (well-formed but
  conflicts with current state), 422 validation, 404 missing.
- **Idempotent ingest:** the telemetry write is keyed on `event_id` so retries are safe
  ([0003](0003-event-driven-ingestion.md)).
- **OpenAPI** is auto-generated by FastAPI (`/docs`) — the contract is always current.

## Consequences

- Command sub-resources are slightly less "RESTful-pure" than verbs-as-HTTP-methods,
  but they model real operations honestly. A reasonable, defensible trade.

## At production scale

Cursor-based pagination over `limit`; `ETag`/conditional reads; per-operator rate
limiting; explicit API versioning. **Rule of thumb:** state queries and commands are
REST; high-volume telemetry is events, not request/response.
